# MORT production SECURITY DEFINER review — 2026-11-02

## Scope and method

Read-only catalog and source review of all 59 functions in schema `public` with
`prosecdef = true` on production project `jxbnrkasktbhtiujkhay`. No SQL was
applied. The exact source, owner, function configuration, and effective role
grants were checked from PostgreSQL catalogs.

- All 59 are owned by `postgres` and pin `search_path` to the empty path.
- 51 are executable by `authenticated`; one of those is also executable by
  `anon`. Eight have no authenticated execute grant: the five Stripe server
  RPCs, `mort_send_message`, `mort_submit_job_application`, and the location
  version trigger function. All 59 report service-role execute. This does not
  make the auth-gated user functions usable without a user JWT.
- No function source contains dynamic `EXECUTE`.
- `get_runtime_feature_status()` is the sole anon-callable function; it exposes
  operational flags only. Current output says marketplace closed, publishing
  disabled, payments disabled, document collection off, and AI disabled.
- This is a source and privilege review, not a runtime proof for every function.

`Auth` below means `authenticated` plus server role, with anon denied. `Svc`
means `service_role` only; `anon` and `authenticated` are denied. `Public status`
means anon/authenticated/service role. The trigger function is not a client RPC.

## Remediation queue

1. **Required before relying on live verification:** harden `mort_review_verification_case` so a reviewer cannot set `verified` without a submitted, case-type-appropriate evidence/provider result or an explicitly authorized, audited manual exception.
2. **Required for block/accept ordering:** take the same sorted user-pair advisory lock in `mort_accept_job_application` before checking `user_blocks`; add a two-session regression test.
3. **Required if school verification expires:** recheck all role-required current verification tracks in application eligibility and acceptance, not age alone; test expiry/revocation behavior.
4. **Check-in contract cleanup:** honor the check-in completion request ID and enforce the active assignment lifecycle at completion.
5. **Product-policy check:** specify what Guardian revocation does to an in-progress assignment and whether skipping Guardian setup may coexist with an active link.

No remediation above was applied to production in this review.

## Leaked-password protection and cost

Supabase documents HaveIBeenPwned password blocking as Pro-and-above only. The current public pricing lists Pro at **$25/month**; it includes $10/month compute credit for a default Micro instance, and additional project compute/usage may add cost. This is an organization subscription change, so the actual monthly total depends on MORT's organization and project compute. The isolated Auth API rejected the prior enable attempt with HTTP 402; current read-only config remains false on production and isolated. No plan or Auth configuration was changed.

Without upgrading, use the available password-policy controls: set a minimum of at least 8 characters, require a strong character mix, enable MFA where appropriate, keep email confirmation and rate limiting, and coach against password reuse/use of a password manager. These reduce risk but are **not equivalent** to server-side known-breached-password rejection. Do not build a custom password checker or send passwords to a third party as a substitute without a separate privacy/security design.

# MORT password guard: phased Flutter rollout

This review candidate is for `mortapp/Mort` and `flutter_mort`. It preserves MORT's own leaked-password protection; no Supabase plan change is a prerequisite. [#109](https://github.com/mortapp/Mort/pull/109) and [#118](https://github.com/mortapp/Mort/pull/118) supplied the original contract and DOB check. This candidate does not include Swift-reference modifications. Hosted QA `ckcxakhxqlkhppsxxjhv` runs the older guard; this revision is not deployed to either hosted project.

## Contract

- Flutter uses `password-guard` for signup and recovery, never retries a password write directly with Auth, and continues using ordinary Auth for sign-in and initiating recovery. Invalid and under-13 signup dates are rejected before breach checking or Auth.
- The guard checks MORT's password policy and sends only the five-character SHA-1 prefix to [Have I Been Pwned](https://haveibeenpwned.com/API/v3#PwnedPasswords). Breach-service and signup-quota failures stop password writes, not just warnings.
- `staged` is explicit and sends no attestation fields. It checks all guard-mediated writes but leaves older clients and direct Auth writes unchanged. It must never be reported as database enforcement.
- `enforced` is the default. The Edge function confirms all four Auth triggers are active and a Vault secret is present before minting. The Auth triggers verify and consume each attestation, reject direct nonempty password writes, and strip attestation metadata from Auth users and identities. Only `service_role` may call the quota and readiness RPCs; Auth calls still use the public app key plus a real user session where applicable.
- `maintenance` and unknown modes refuse password writes through the guard. Ordinary Auth sign-in is not a guard call. Missing Edge attestation configuration also fails closed in enforced mode.

## Review and staged deployment order

1. Independently confirm the target project and compare migration hashes and the Auth catalog with the approved preflight. Only approve the exact reviewed artifact and target. Never apply the entire pending list to a hosted project. Do not rewrite the historic QA migration or assume this candidate's bytes are already running there.
2. For a new rollout, install `20261121200000_password_guard_signup_quota_stage.sql` alone and verify grants. Configure the staged guard independently. Test rejection, signup, confirmation, sign-in and recovery with the candidate Flutter clients and controlled inboxes; confirm that supported legacy clients remain compatible. QA already has the older enforcing triggers; do not turn those off to demonstrate a staged rollout. Rehearse staged mode in an isolated replica, and use a separately reviewed forward-only plan for hosted QA.
3. Approve supported-client minimum versions, recovery fallback procedures, separate Vault and Edge configuration in each environment, SMTP capacity, quotas and monitoring. Staff provisioning must use passwordless Auth invitations and a real invite session followed by guarded password setup; granting staff roles is a separate action. Verify Apple and Google OAuth with actual providers; local invitation and sign-in tests do not prove OAuth.
4. In a separate authorized activation window, pause guarded writes using `maintenance` and verify the prior instances have drained. Provision matching attestation secrets in Vault and Edge without logging or printing them. Apply only `20261121200100_server_enforced_password_attestation.sql`, inspect the four installed triggers and RPC ACLs, then set `enforced`. Verify guard signup and recovery, direct-write denial, sign-in, no leaked metadata, and the OTP/invite and OAuth flows actually in service. Stop and follow the approved rollback plan if any check fails.
5. For an authorized rollback, enter `maintenance` and drain enforced instances before running the [trigger rollback](../../supabase/production-baseline-recovery/20261121200100_password_guard.rollback.sql). Confirm the trigger and readiness states, then return to `staged`; leave the quota in place for the guarded Flutter client. This restores compatibility, not database-wide protection. Reverify signup, recovery and ordinary sign-in, and report enforcement as off. Rotate secrets under the same maintenance boundary; do not remove the triggers while an old instance can still mint an attestation.

The readiness check is a runtime guardrail, not a substitute for the rollout window or for verifying the exact deployed trigger definitions. A disposable Supabase replica exercises real Auth signups, password changes and recovery against local SMTP, using only a fixture breach lookup. Provider, store and hosted QA results are separate release gates.
